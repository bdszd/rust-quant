# Rust Quant 后端 Worker 扩展性能测试记录

## 1. 测试目的

本次测试主要研究 Rust Quant 后端在不同并发负载下，增加 Worker 数量能否提高任务处理能力。

重点关注：

- Worker 数量对任务吞吐量的影响。
    
- Worker 数量对任务创建延迟的影响。
    
- Worker 数量对端到端任务完成时间的影响。
    
- 不同并发负载下，Worker 扩容是否存在收益。
    
- 系统是否出现任务丢失、HTTP 请求失败或任务超时。
    

本次测试不以单纯提高 Worker 数量为目标，而是通过对照实验，观察当前后端架构的扩展能力。

## 2. 测试环境

### 2.1 后端架构

```
Client / k6
    |
    v
Axum API
    |
    v
PostgreSQL
    |
    +---- backtest_tasks
    |
    +---- backtest_outbox
                |
                v
        Outbox Publisher
                |
                v
            RabbitMQ
                |
          +-----+-----+
          |           |
       Worker 0    Worker 1 ...
          |           |
          +-----+-----+
                |
           Backtest Core
                |
           PostgreSQL
```

主要组件：

|组件|职责|
|---|---|
|Axum|HTTP API 接入|
|PostgreSQL|任务状态、Outbox 和回测结果持久化|
|Transactional Outbox|保证任务创建与消息发布记录的一致性|
|Outbox Publisher|将待发布任务发送到 RabbitMQ|
|RabbitMQ|任务消息分发|
|Worker|消费消息、认领任务并执行回测|
|Backtest Core|执行回测计算|
|k6|模拟并发用户并进行端到端测试|

```

## 3. 测试方法

使用 k6 对后端进行端到端压测。

测试脚本：

```
tests/load/backtest_e2e.js
```

测试流程：

```
1. 创建回测任务
       |
       v
2. 获取任务 ID
       |
       v
3. 定期轮询任务状态
       |
       v
4. 等待任务进入终态
       |
       v
5. 记录任务完成情况
```

每次测试持续约 50 秒。

测试过程中主要统计：

|指标|含义|
|---|---|
|accepted_tasks|成功提交的任务数量|
|completed_tasks|完成的任务数量|
|create_task_duration|创建任务的 HTTP 请求耗时|
|task_completion_duration|从创建任务到轮询发现任务完成的耗时|
|http_req_duration|HTTP 请求整体耗时|
|http_req_failed|HTTP 请求失败率|
|poll_errors|任务状态轮询错误数|
|timeout_tasks|超时任务数量|

注意：

`task_completion_duration` 包含任务排队、消息传递、执行和轮询等待时间，不等于 Worker 的纯执行耗时。

另外，k6 的 `stages` 中 `target` 表示阶段结束时的 VU 目标值，VU 数量会在阶段内逐渐变化，并非整个阶段始终保持目标 VU 数量。

## 4. 测试矩阵

本次使用三组负载：

|测试组|VU Stages|主要观察目标|
|---|---|---|
|A：低负载|1 → 3 → 5 → 0|观察低并发下 Worker 扩容效果|
|B：中负载|5 → 10 → 20 → 0|观察中等并发下 Worker 扩容效果|
|C：高负载|10 → 25 → 50 → 0|观察较高并发下 Worker 扩容效果|

每组分别测试：

```
2 Worker
4 Worker
8 Worker
```

总计 9 组测试。

所有测试均使用 4929 行数据集，保持任务参数和测试时长一致。

观察：

5. 低负载下，2 Worker 已经能够及时处理任务。
    

初步结论：

低并发情况下，增加 Worker 数量没有带来明显收益。

```

测试结果：

|指标|2 Worker|4 Worker|8 Worker|
|---|---|---|---|
|完成任务|317|310|301|
|吞吐量（tasks/s）|6.24|6.14|5.94|

观察：

5. 8 Worker 的任务完成平均耗时达到 1.44 秒。
    
6. 三种配置均没有出现 HTTP 错误、轮询错误和任务超时。
    

初步结论：

在当前中等负载下，增加 Worker 数量没有提高系统吞吐量，反而出现了轻微的性能下降。

## 6. 结果分析

### 6.1 Worker 扩容没有带来吞吐量提升

三组测试呈现出比较一致的趋势：

- 低负载：Worker 数量增加，吞吐量基本不变。
    
- 中负载：Worker 数量增加，吞吐量反而下降。
    
- 高负载：2 Worker 和 4 Worker 基本持平，8 Worker 略有下降。
    

目前没有证据表明增加 Worker 数量能够改善当前系统的任务处理能力。

### 6.2 可能存在 Worker 之外的瓶颈

当前任务处理链路：

```
HTTP 请求
    |
    v
创建任务
    |
    v
PostgreSQL 写入
    |
    v
Outbox Publisher
    |
    v
RabbitMQ
    |
    v
Worker 消费
    |
    v
数据库认领任务
    |
    v
Backtest Core 执行
    |
    v
保存回测结果
    |
    v
RabbitMQ ACK
```

Worker 数量只是其中一个环节。

即使增加 Worker，如果其他环节无法提供更高的处理能力，整体吞吐量也不会明显提升。

可能需要进一步检查：

- PostgreSQL 写入和更新耗时。
    
- Outbox Publisher 的发布速度。
    
- RabbitMQ 消息投递和确认耗时。
    
- Worker 数据库认领任务的耗时。
    
- Backtest Core 的实际执行耗时。
    
- 回测结果持久化耗时。
    
- CPU、内存和磁盘 I/O 资源竞争。
    

目前这些只是待验证的瓶颈假设，不能仅凭本次测试认定具体瓶颈。

### 6.3 API 创建延迟也受到影响

创建任务 P95：

|负载|2 Worker|4 Worker|8 Worker|
|---|---|---|---|
|低负载|7.66ms|8ms|53.47ms|
|中负载|295.38ms|489.75ms|321.03ms|
|高负载|453.27ms|777.57ms|701.45ms|

在中、高负载下，创建任务延迟明显高于低负载。

值得注意的是，创建任务发生在 Worker 执行之前，因此 API 延迟不能简单归因于 Worker 执行时间。

需要结合 PostgreSQL、Outbox 写入和 API 资源使用情况进一步分析。

### 6.4 系统稳定性

九组测试均满足：

```
HTTP 请求失败率：0%
Poll Errors：0
Timeout Tasks：0
```

每组测试完成数量均等于成功提交数量。

这说明在本次测试范围内，系统能够正常完成任务处理，没有观察到任务丢失或明显的稳定性问题。

但这不代表系统已经验证了故障恢复、重复投递、进程崩溃等场景下的可靠性。

## 7. 当前结论

本轮 Worker 扩展测试得到以下结论：

1. 低负载下，2 Worker 已经足以处理当前任务流量。
    
2. 中负载下，增加 Worker 数量没有提高吞吐量。
    
3. 高负载下，4 Worker 相比 2 Worker 没有明显优势。
    
4. 8 Worker 在三组测试中均未体现出明确的扩容收益。
    
5. 当前系统在九组测试中均完成了全部已接受任务，没有出现 HTTP 失败和任务超时。
    

因此，现阶段没有充分理由将 Worker 数量从 2 提高到 4 或 8。

后续应优先定位完整任务链路中的耗时分布，而不是继续盲目增加 Worker。

## 8. 后续性能分析方向

下一阶段重点是增加链路级时间统计。

建议将一次任务拆分为以下阶段：

|阶段|需要记录的时间|
|---|---|
|API|HTTP 请求处理耗时|
|PostgreSQL|任务与 Outbox 写入耗时|
|Publisher|Outbox 读取到消息发布成功耗时|
|RabbitMQ|消息发布、消费及确认耗时|
|Claim|Worker 认领任务耗时|
|Backtest Core|实际回测执行耗时|
|Persistence|回测结果及任务状态保存耗时|
|ACK|Worker 确认消息耗时|

通过这些指标确定真正的性能瓶颈，再针对具体环节进行优化。
