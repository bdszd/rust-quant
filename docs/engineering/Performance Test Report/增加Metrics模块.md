Metrics模块主要是一些数据流对应处理节点的的计数器合集。
# Rust Quant 回测后端：Metrics 增强与并发压测阶段分析

> **阶段范围**：从首次增加阶段级 Metrics、发现数据库相关耗时偏高，到进一步拆分数据库操作并完成两组并发压测。  
> **本阶段有效记录**：3 / 5 / 10 VUs 汇总组（154 个任务）；10 / 20 / 40 VUs 汇总组（255 个任务）。  
> **统计口径**：两组数据均为多个并发档位运行后，在同一后端进程生命周期内读取到的累计 Metrics，不代表每个 VU 档位各自独立的结果。

---

## 1. 阶段背景与目标

前一阶段，我们已经完成了回测任务的异步处理链路：

1. API 接收回测请求；
2. PostgreSQL 保存任务记录和 Outbox 记录；
3. Publisher 查询 Outbox，将任务发布到 RabbitMQ，并等待 Publisher Confirm；
4. Worker 从 RabbitMQ 消费任务；
5. Worker 将回测计算放到 `spawn_blocking` 中执行；
6. 回测结果写回 PostgreSQL；
7. Worker ACK 消息。

链路已经能够正常运行，但仅凭接口响应时间、任务成功率和整体完成时间，我们还无法判断系统内部究竟慢在哪里。

因此，这一阶段的重点不是马上优化代码，而是先建立一套能够解释系统耗时的 Metrics：

- 看清一个任务经过哪些阶段；
- 区分数据读取、数据校验、回测计算、数据库操作和 RabbitMQ 操作；
- 同时观察平均耗时、P95 和 P99，识别长尾；
- 根据实际数据定位问题，而不是凭感觉增加 Worker 数量或数据库连接数。

## 2. 第一轮 Metrics：发现数据库相关路径耗时偏高

### 2.1 第一轮主要观测点

最初增加的 Metrics 主要覆盖任务处理链路中的关键阶段：

|指标|含义|
|---|---|
|`api_create_backtest`|API 创建回测任务的整体耗时|
|`data_load`|读取行情数据的耗时|
|`data_validate`|行情数据校验耗时|
|`engine_execute`|回测引擎执行耗时|
|`worker_claim`|Worker 领取任务的耗时|
|`result_persist`|回测结果持久化的整体耗时|
|`rabbitmq_publish_confirm`|RabbitMQ 发布消息并等待确认的耗时|
|`rabbitmq_ack`|Worker 消费完成后 ACK 的耗时|

### 2.2 第一轮测试结果

此前一次独立的 20 VUs 测试中，主要结果如下：

|指标|结果|
|---|---|
|成功任务|207 / 207|
|HTTP 请求失败率|0%|
|创建请求 P95|518.54 ms|
|`engine_execute` 平均耗时|6.24 ms|
|`engine_execute` P95|13.17 ms|
|`result_persist` 平均耗时|183.75 ms|
|`result_persist` P95|429.49 ms|
|`db_insert_task` 平均耗时|92.31 ms|
|`db_insert_task` P95|395.52 ms|

从这组数据中，我们发现了一个明显现象：

**回测引擎本身执行很快，而任务创建和结果持久化等数据库相关路径耗时明显更高。**

但当时的 `db_insert_task` 和 `result_persist` 仍然是较粗粒度的指标。它们只能说明数据库相关流程耗时较高，无法准确回答具体原因：

- 是否在等待连接池分配连接？
- 是否事务开始或提交耗时较高？
- 是否具体数据库调用耗时较高？
- 是否在写入数据库之前，JSON 序列化就已经消耗了较多时间？
- Outbox 查询和状态更新是否也存在长尾？

因此，我们没有直接把问题定性为某条 SQL 慢，而是继续细拆数据库相关流程。

## 3. 第二轮改造：细拆数据库相关 Metrics

### 3.1 改造目标

这次改造的核心是：

**把原本笼统的数据库耗时，拆成连接获取、事务、具体数据库操作和序列化等更细的观测点。**

本次主要修改了四个文件：

|文件|改动内容|
|---|---|
|`apps/backend/src/storage.rs`|在存储流程中拆分连接获取、事务、数据库操作和序列化等耗时|
|`apps/backend/src/api.rs`|记录创建任务过程中各数据库子步骤的耗时|
|`apps/backend/src/worker.rs`|记录 Worker 领取任务、结果序列化和结果持久化的子步骤耗时|
|`apps/backend/src/metrics.rs`|注册、汇总新增指标，并在 `/api/metrics` 中暴露数据库连接池状态|

这次改造主要增加观测埋点，没有改变原来的任务处理架构。我们仍然使用 PostgreSQL Outbox、RabbitMQ Publisher/Consumer 和 Worker 执行链路，只是让每个关键步骤的耗时变得可见。

### 3.2 新增的 Metrics 测试点

#### A. 数据库连接池获取

|指标|观测内容|
|---|---|
|`db_acquire_insert_task`|API 创建任务时获取数据库连接的耗时|
|`db_acquire_claim_task`|Worker 领取任务时获取数据库连接的耗时|
|`db_acquire_result_persist`|保存回测结果时获取数据库连接的耗时|

这组指标用于判断操作是否在连接池处等待，而不是直接执行数据库操作。

#### B. 事务与数据库操作

|指标|观测内容|
|---|---|
|`db_tx_begin`|开始数据库事务的耗时|
|`db_task_insert`|插入任务记录的耗时|
|`db_outbox_insert`|插入 Outbox 记录的耗时|
|`db_claim_update`|更新任务领取状态的耗时|
|`db_result_update`|更新任务结果和状态的耗时|
|`db_tx_commit`|提交事务的耗时|
|`outbox_query`|Publisher 查询待发送 Outbox 记录的耗时|
|`outbox_update`|更新 Outbox 记录状态的耗时|

这些指标让我们能够区分任务创建、Worker 领取任务、结果保存以及 Outbox 发布流程中的不同数据库操作。

需要注意：例如 `db_result_update` 记录的是对应数据库调用的整体耗时。它可以帮助定位到具体操作，但不能仅凭这个数值就断言 SQL 执行计划、索引或 SQL 本身存在问题。调用耗时还可能受到数据库排队、锁等待、网络和其他因素影响。

#### C. 序列化

|指标|观测内容|
|---|---|
|`db_serialize_job`|任务内容序列化耗时|
|`db_serialize_result`|回测结果序列化耗时|

增加序列化指标，是为了对写入数据库前的 CPU 工作进行单独观察，避免将序列化时间全部归入数据库操作。

#### D. 数据库连接池状态

同时，`/api/metrics` 增加了连接池状态：

```
{
  "database_pool": {
    "size": 10,
    "idle": 10,
    "busy": 0,
    "max_connections": 10
  }
}
```

字段含义：

- `size`：当前连接池中的连接数量；
- `idle`：当前空闲连接数量；
- `busy`：当前正在使用的连接数量；
- `max_connections`：连接池允许的最大连接数。

这是一份读取 Metrics 时的瞬时快照，不是压测期间的连接池峰值或时间序列。压测结束后看到 `idle = 10`、`busy = 0`，只能说明读取指标的那个时刻连接已经空闲，不能据此判断整个压测期间是否发生过连接等待。

## 5. 压测数据分析

### 5.1 回测引擎不是当前主要瓶颈

两组数据中：

- `engine_execute` 平均耗时分别约为 5.16 ms 和 6.57 ms；
- P95 分别约为 11.86 ms 和 14.40 ms。

与 `result_persist` 的平均 147.00 ms 和 199.02 ms 相比，回测计算耗时明显更低。

这说明在当前数据规模和策略场景下，系统耗时主要不在回测逻辑的计算过程。继续优化回测算法，未必能显著降低整个任务的端到端耗时。

### 5.2 结果持久化是值得重点关注的阶段

`result_persist` 的整体耗时：

|汇总组|平均耗时|P95|P99|
|---|---|---|---|
|3 / 5 / 10 VUs|147.00 ms|345.37 ms|638.41 ms|
|10 / 20 / 40 VUs|199.02 ms|471.40 ms|876.24 ms|

进一步拆分后：

- `db_serialize_result` 平均耗时约为 87.66 ms / 95.09 ms；
- `db_result_update` 平均耗时约为 50.67 ms / 81.29 ms。

这说明结果保存路径并不只是数据库更新本身在花时间，**结果序列化也占据了明显的耗时**。

因此，不能把 `result_persist` 的全部耗时都归因于 SQL。更准确的结论是：结果持久化阶段由结果序列化、连接获取、数据库更新以及相关事务流程共同构成，其中序列化和结果更新都值得继续观察。

### 5.3 任务创建路径出现连接获取和事务长尾

在 10 / 20 / 40 VUs 汇总组中：

- `db_acquire_insert_task` 平均 77.19 ms，P95 419.60 ms；
- `db_tx_begin` 平均 24.81 ms，P95 175.07 ms；
- `db_task_insert` 平均 18.42 ms，P95 145.14 ms；
- `db_outbox_insert` 平均 15.62 ms，P95 114.41 ms；
- `db_tx_commit` 平均 18.60 ms，P95 132.59 ms。

其中，连接获取阶段的 P95 和 P99 比较突出，说明这组混合并发负载下，任务创建路径存在明显的连接获取等待长尾。

不过，当前连接池指标只记录了读取时的状态，没有压测期间的时间序列。因此可以说连接获取耗时出现长尾，但还不能仅凭结束时 `idle = 10` 就证明或否定连接池在压测期间是否达到容量上限。

### 5.4 Outbox 查询出现长尾

`outbox_query` 的结果：

|汇总组|样本数|平均耗时|P95|P99|
|---|---|---|---|---|
|3 / 5 / 10 VUs|111|8.71 ms|21.12 ms|159.49 ms|
|10 / 20 / 40 VUs|120|41.71 ms|380.12 ms|573.62 ms|

这里的样本数少于任务数，是因为 Publisher 周期性查询 Outbox，而不是每个任务固定执行一次查询。

后一组数据的 `outbox_query` P95 达到约 380 ms，值得关注。但它是 Publisher 轮询阶段的查询耗时，不能直接当成每个任务的数据库查询耗时，也不能仅凭这一项断言 Outbox SQL 缺少索引。

### 5.5 数据读取耗时高于回测计算

两组 `data_load` 平均耗时分别约为 50.29 ms 和 62.45 ms，P95 分别约为 89.84 ms 和 108.59 ms。

相较之下，`data_validate` 平均只有约 1.90 ms 和 2.29 ms。

在当前数据集下，读取行情数据的成本高于数据校验，也明显高于回测引擎计算。它是一个值得记录的固定开销，但从目前的 P95 看，暂时没有结果持久化和数据库相关阶段那么突出的长尾。

### 5.6 RabbitMQ 暂时不是主要耗时来源

两组 `rabbitmq_publish_confirm` 平均耗时约为 8.15 ms 和 10.03 ms，P95 约为 18.76 ms 和 38.59 ms。

`rabbitmq_ack` 平均耗时约为 4.14 ms 和 7.60 ms，P95 约为 6.76 ms 和 19.98 ms。

结合两组任务全部成功、发布确认失败为 0、ACK 失败为 0 的结果，目前没有证据表明 RabbitMQ 是这轮压测的主要性能瓶颈。

## 6. 本阶段结论

这一阶段完成了从“发现整体慢点”到“拆开内部耗时”的过程。

### 已经确认的事实

1. 两组汇总压测均完成了全部任务，没有观察到任务失败、RabbitMQ 发布失败或 ACK 失败。
2. 当前回测计算耗时较低，`engine_execute` 不是主要瓶颈。
3. 结果持久化阶段耗时明显高于回测计算阶段。
4. 结果序列化本身占据了显著时间，不能把持久化耗时简单等同于 SQL 执行耗时。
5. 任务创建路径的连接获取、事务和数据库调用存在长尾，尤其在 10 / 20 / 40 VUs 汇总组中更明显。
6. Outbox 查询在后一组数据中出现较明显的长尾，需要结合 Publisher 轮询行为继续观察。
7. RabbitMQ 发布确认和 ACK 的耗时相对较低，目前不是优先怀疑对象。

### 当前还不能下的结论

- 不能说某条 SQL 已经被证实是慢 SQL；
- 不能说连接池在整个压测过程中持续耗尽；
- 不能用两组混合档位汇总数据推导每一个 VU 档位的独立性能；
- 不能仅凭这两组数据断言增加 Worker 或数据库连接数一定会改善性能。

### 本阶段最重要的产出

**我们把原本笼统的数据库耗时，拆成了连接获取、事务开始、具体数据库调用、事务提交、序列化和 Outbox 轮询等观测点。**

现在，性能分析已经从“数据库相关操作比较慢”推进到更具体的方向：

- 结果序列化是否需要优化，结果是否有必要完整写入当前 JSON 字段；
- 结果更新调用的耗时主要来自哪里；
- 任务创建阶段为什么会出现连接获取长尾；
- Outbox 轮询查询的长尾是否与查询批次、轮询频率或数据库负载有关。

这些是后续可以进一步验证的问题，而不是当前数据已经证明的原因。

### 统计口径提醒

- Metrics 在后端进程内累计。如果多个压测档位在同一个后端进程生命周期内运行，读取到的就是累计数据。
- 要得到每个并发档位独立的 Metrics，需要每档测试前重启后端进程，并在该档测试结束后单独读取 `/api/metrics`。
- `database_pool` 当前是读取时的瞬时快照；如需分析峰值和等待情况，需要增加周期采样或连接池事件级指标。
- 阶段耗时存在包含关系。例如 `result_persist` 是整体阶段，内部的序列化、连接获取和数据库更新是其子步骤。分析时不能把父阶段和子阶段相加后当作总耗时。
- 不同阶段的样本数也可能不同。例如 `outbox_query` 是 Publisher 周期轮询采样，不能要求它与任务数相等。
